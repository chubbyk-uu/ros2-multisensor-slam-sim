# 验证方法与实验设计

本页记录本项目如何把“看起来有效”变成可解释的证据。性能数值见
[性能与标定](performance.md)，每条链路的验收结论见[验收记录](acceptance.md)，
失败的具体根因见[工程事件](incidents.md)。完整的历史对照表保留在
[性能历史档案](archive/performance-chronicle.md)。

## 基本规则

1. 先测量，再改参数。提出性能或精度问题时，先区分输入、估计、地图、导航和
   宿主调度；不要用一次成功或一次失败直接归因。
2. 一次只改变一个可解释因素。若必须多项一起改，只能验证组合可用，不能声称
   单个改动带来收益。
3. 真值只作评分。控制器或 SLAM 不得消费 `/ground_truth/odom`；测试控制层为
   复现路线使用真值时，必须明确隔离其数据流。
4. 阈值必须有来源。采用历史分布、物理几何或固定输入测量，并记录余量；不能
   用同一批数据既调门限又宣称独立验收。

## 固定输入与活动仿真互补

固定 MCAP 能排除传感器随机性，适合比较扫描匹配、回环、地图重建和快照恢复；
它不能保证异步后台任务的提交顺序完全相同，也不能覆盖导航与物理交互。

Gazebo 活动回归能验证控制、Nav2、探索、碰撞和启动/退出，但受物理步进与调度
影响。活动结果必须报告分布而不是只报单次末值，并记录宿主健康信号和进程清理。
两者的输入契约、哈希和回放方式见[固定数据集](datasets.md)。

## A/B 对照的三个层次

### 正交分解

当两个参数同时影响一个表象时，使用 2×2 或等价的正交对照。例如探索二维投影中，
`occupied_minimum` 只改变占据侧，`maximum_ray_range` 只改变射线积分范围；固定包
对照避免了把“墙体变强”和“地图变小”误认成同一个收益。完整表见
[历史档案](archive/performance-chronicle.md#固定包-ab两项改动的正交分解)。

### 同对象直接对照

优先测量被修对象而不是间接代理。地图全局拉伸事件中，前端位姿和地图系位姿分开
对真值评分；零回环、前端误差同为 `0.031 m` 的两次运行中，修复使地图系误差由
`2.717 m` 降至 `0.030 m`。这比“地图看起来更方正”更能证明因果。

### 离线选择回放

Frontier 候选日志记录每次决策的完整候选和评分分量，因此可离线比较 band、top-k
和 softmax 的触发率与额外路径代价。它只回答单次决策：一旦实际目标不同，后续世界
状态也不同，整趟覆盖和完成时间仍需活动运行验证。

回放输入保留在 `docs/results/`：
[决策日志](results/2026-08-11-frontier-selection-decisions.log)、
[新 seed 决策日志](results/2026-08-11-fresh-seed-decisions.log) 与
[目标序列](results/2026-08-11-exploration-goal-sequences.txt)。

## 重复运行、随机性与活动 campaign

重复运行前先定义结果类别：核心 FAIL、PASS、`INFRA_UNSTABLE` 与 `VOID`。后两者
不是“悄悄重跑”的借口：必须单独计数，达到批次上限则整批无效。控制/规划降频、
碰撞和恢复都可能同时反映主机负载与导航缺陷，因此条件化过滤必须在文档中说明。

随机化应作用于真正改变初始条件的变量。探索器曾对近优 frontier 加随机选择，但
多数决策候选池只有一个元素，路线仍高度相似；随后改为从 SDF collision 几何中采样
安全随机出生点。随机出生记录必须包含 seed、世界 SHA-256、采样参数、栅格边界和
源码线索；仅记录 seed 不能保证复现。

随机化近优选择本身的十次活动批次见
[`2026-08-11-randomised-selection-campaign.json`](results/2026-08-11-randomised-selection-campaign.json)：
`10/10` 可评估运行通过，但这只证明改动未引入回退，不证明随机化带来收益。

2026-08-12 的三世界首批 15 次是**标定批次**，门限来自该批自身；随后的新 seed
15 次才是独立验证。两批都保留，以防把“历史可运行”误说成“独立证明”。

## 故障注入验证跨进程归因

单元测试只能证明某一层的局部行为。对于探索器，必须另验证：节点发布故障分类、
回归提前读取分类并给出 verdict、campaign 将 verdict 归档。启动期未 activate 与
运行期失活注入还验证墙钟预算：暂停 Gazebo 后 `/clock` 停止，若错误使用仿真时钟，
故障不会超时。

## 封路与动态障碍的判据

导航安全验收有两个场景，判据相反，必须分开写：

- **可绕行**（动态障碍横在路上，但仍有通路）：目标必须到达，且全程无碰撞。
- **不可绕行**（完全封路）：目标必须**失败**，机器人必须安全停下。

这不需要第四类 verdict。`PASS`/`FAIL`/`INFRA_UNSTABLE` 已经分区完备，而“正确地
失败”是封路场景的**通过判据**，不是第三种运行结局。Nav2 在封路运行中真的挂掉，仍
按 `(dependency_lost, nav2_runtime_lost)` 归为 `INFRA_UNSTABLE`，闭集不变。

### 没撞上不等于正确放弃

一台从未感知到路障、因无关原因停下的机器人，能轻松通过“未碰撞且未到达”的检查。
判据因此必须要求**正面证据**，三条同时成立才算通过：

1. 路障在代价地图中被标记为致命格（证明它被感知到，而不是被漏掉）；
2. 规划器报告无可行路径（证明它尝试过并得出结论，而不是从未规划）；
3. 机器人进入静止（证明它停下，而不是仍在向障碍推进）。

缺任何一条都不是安全停车，而是巧合。

### 超时在这个场景里不是基础设施问题

`exploration_campaign` 把 launch 超时归为 `INFRA_UNSTABLE`，理由是“挂死的 launch
说明不了探索算法的任何事”。这条理由在封路场景里不成立：**无限恢复正是本场景要测
的缺陷**，把它归给环境等于把待测故障判成免责。

因此封路回归必须持有自己的墙钟预算——“到此为止就该放弃了”——并且这个预算显著短于
launch 超时。超出预算即 `FAIL`。封路运行绝不能由 launch 超时来结束；一旦是它结束
的，说明回归的预算设得太松，结果无效。

### 恢复次数既要有下限也要有上限

不做任何恢复就放弃同样是错的：那说明规划失败没有触发恢复链。判据取区间——至少尝试
一次恢复，且不超过预算上限。上限归入既有的 `navigation_behaviour` 类检查（主机不
健康时可降级为 `INFRA_UNSTABLE`），下限归入核心检查（与主机负载无关）。

### 覆盖范围

现状是 `navigation_regression.py` 只覆盖 2D 链路的动态障碍：注入 `0.60 × 0.60 ×
0.80` 箱体、以代价地图消息时间戳计量致命格标记时延、检查绕行且无碰撞。3D 链路没有
对应实现，两条链路都没有封路场景。三块都要补齐，且两条链路共用同一套判据，否则
“3D 也验过了”会变成一句无法核对的话。

## 结果保留与可复核性

- `docs/results/` 保存小型 JSON 摘要、输入身份和 verdict；大日志放在工作目录，
  不提交仓库。
- 结果文件中的源码 commit 与 dirty 标记只能定位行为来源；install 中的 C++ 二进制
  可能早于工作树，二者不是构建可复现保证。
- 快照、地图和固定包的格式变更必须显式版本化；不能以修改 JSON 字段假装旧数据
  已按新 schema 验证。
- 迁移或整理文档时，原始数字应留在历史档案并以标题链接，而不是仅保留口头结论。
