# 故障归因与工程事件

本文记录已经定位的工程故障：影响范围、根因、修复和验证证据。日常操作请先看
[常见问题](troubleshooting.md)；性能数字和完整实验上下文见
[性能与标定](performance.md)。

## 阅读约定

- “已修复”表示代码路径和相应自动检查均已落地；不等同于 Gazebo 或宿主机
  本身永远不会发生故障。
- 真值只用于定位根因和离线评分，从不进入 SLAM、EKF 或 Nav2 的估计输入。
- 结果 JSON 是可复核的验收证据；临时日志若未保留，会明确标为历史观察，
  不把它当作可复现实验。

## 2D 自研 SLAM：回环、退化与实时性整改

2026-07-30 的工程审查集中暴露了未优化构建、回环阻塞激光回调、地图重建
饥饿、异常穿透、Path 带宽、扫描输入有限性和回环事务性等问题。整改后的
2D 基线采用后台状态快照处理回环、事务式合并约束、节点时钟地图重建和有限性
校验；详细处理表与固定包、走廊、重复结构和大场景验证见
[2026-07-30 审查整改档案](archive/2026-07-30-review-remediation.md)。

平行走廊中的沿轴滑动不能用相关分数曲面的 Hessian 判断：离散光束端点会制造
假曲率，使检测随噪声和子图深度翻转。运行时已改用保留原始光束索引、检查表面
断裂的扫描法向信息矩阵，并连续缩放弱方向修正。正常闭环与快速旋转回归同时要求
零退化误报，走廊中段则要求足够的真实退化检出。

## 3D 复合启动：scoped launch 与延迟求值

**症状。** 三个包含 RTAB-Map 的复合回归入口在点云契约检查完成后报
`launch configuration 'reset_database' does not exist`，随后中止。

**根因。** `GroupAction(scoped=True)` 正确隔离 include 参数，但
`rtabmap_3d.launch.py` 把 `LaunchConfiguration` 的解析推迟到进程退出事件。
事件触发时作用域已销毁，延迟读取失效。

**修复与验证。** 在作用域有效时用 `OpaqueFunction` 捕获参数实际值，再将
值交给事件处理器。保留延迟求值、仅切换 scoped 的 A/B 证明 scoped 是触发
条件而不是根因；修复后两圈回归 `17/17 PASS`。五个复合入口还增加了无界面
启动冒烟检查，要求关键节点持续在线并检查异常栈、作用域错误和子进程死亡。

## RTAB-Map 平面导航：六自由度 ICP 造成地面假障碍

**症状。** 物理上可通行的走廊被 Nav2 判为无路，局部障碍层出现围绕机器人的
同心弧线。

**根因。** 平面机器人使用了默认六自由度 ICP；`map -> odom` 出现非零高度、
横滚和俯仰，远处地面点因此越过地面高度门限。

**修复与验证。** 启用 `Reg/Force3DoF=true` 和
`RGBD/ForceOdom3DoF=true`，保留三维点云但将轨迹约束为 `x/y/yaw`。结构化
导航回归把 `map -> odom` 高度、横滚和俯仰列为硬判据；高门洞必须通过，
上粗下细的蘑菇柱必须绕行。

## 探索地图：三态投影的两次分类错误

**边界被部分观测格遮挡。** log-odds 栅格中一次到三次 miss 的格子既不属于
自由也不属于未知，若发布为独立中间态，free-to-unknown frontier 会被遮挡，
探索器错误宣布完成。地图生产者现在输出严格三态：可靠自由、可靠占据和未知；
部分证据的自由空间证据仍用于射线清空，但不能伪装成可通行自由格。

**墙被发成未知。** 将“部分观测”统一发成未知后，弱占据墙体又对净距计算
不可见，邻接自由格会被误认为 frontier，目标可能落在墙内。整改把
`occupied_minimum` 与投影射线距离拆成固定包 2×2 对照：阈值增强占据侧，
有限投影距离避免远距掠射侵蚀墙体。随后活动验收不再出现该失败形态。

两次事件说明“未观测”和“证据不足”不能共享一个导航语义。完整 A/B 数字和
多次运行分布见[性能历史档案](archive/performance-chronicle.md#3d-frontier-exploration-首次端到端验收)。

## 探索地图：全局拉伸并非前端漂移

**症状。** 少量运行中已知地图向相反方向同时外扩，包围盒异常增大；前端误差
却仍很小。

**根因。** 未参与位姿图优化的全局关键帧按裸轮速里程计位姿重建，忽略了同一
状态中更准确的扫描匹配位姿；而 `map -> odom` 又只在接受回环后更新。单趟探索
通常没有回环，整张地图因此按轮速漂移绘制。

**修复与验证。** 统一从 `map_from_local * front_end_base_pose` 推导未优化帧和
`map -> odom`。同场景、同为零回环、前端误差同为 `0.031 m` 的直接对照中，
地图系误差从 `2.717 m` 降到 `0.030 m`，越界从 `2.600 m` 降到 `0.000 m`。
后续十次运行的地图系位置误差为 `0.012–0.091 m`，已纳入核心验收判据。

## Nav2 依赖失活不能被解释为地图完成

**症状。** 动作服务器在 DDS 图中可见但尚未 activate，或运行中失活；旧实现
会把被拒绝的目标记为不可达，最终可能错误完成探索并覆盖快照。

**修复。** 可用性预算只在地图、TF 和可达 frontier 已具备后开始，以墙钟计时。
预算内拒绝重试而不拉黑；只有超时后才进入明确 fault。探索器通过闭集
`failure_class` / `failure_code` 报告依赖失效，回归在普通地图检查前读取它，
将其分类为 `INFRA_UNSTABLE`，未知类别或代码则保守地归为核心失败。

**验证。** 启动期 configured 未 activate 和运行期先接受目标再失活的两条故障
注入均提前结束并正确归因为 `INFRA_UNSTABLE`。运行期注入暂停 Gazebo 来冻结
`/clock`，同时验证看门狗确实使用墙钟。

## 宿主污染曾导致错误的 EKF 性能结论

**症状。** 曾观察到 EKF 周期多次错过目标频率。

**根因。** 手工向 `ros2 launch` 父 PID 发 SIGINT 没有回收完整进程树，多个残留
Gazebo、RTAB-Map、EKF 和桥接实例同时发布 `/odom`、`/tf` 并竞争 CPU。

**修复与边界。** 自动回归使用独立进程组并在结束后检查残留。隔离后完整链路仅
观察到一次 `24 ms` 的启动瞬态，不能据旧的污染测量宣称存在长期资源竞争。手动
临时实验也必须按进程组清理，详见[常见问题](troubleshooting.md)。

## 快照：原子写入不等于持久化

版本化快照先写入同目录临时文件、`fsync` 后原子替换，并以写后回读的 FNV-1a
校验和确认落盘字节。原子替换只保证读者不会看到半个文件；没有 `fsync` 与回读
则不能证明掉电或缓存延迟后内容已经持久。版本 5 因此拒绝旧布局而非维护无外部
使用者的兼容分支。固定包 `localization` 恢复回归在 v5 下仍 `11/11` 通过。

## 已知外部边界

Gazebo 有时会在所有 ROS 判据与快照保存完成后的收尾阶段以 `SIGSEGV` 退出。它不
自动证明算法失败，但必须与算法 verdict、进程组清理和是否存在残留进程一起记录；
不能因为“发生在退出时”而无条件忽略。
