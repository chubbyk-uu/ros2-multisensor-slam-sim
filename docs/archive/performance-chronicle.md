# 性能与旋转标定记录

本文记录 2D/3D SLAM 基线的性能优化和里程计标定结果。数值用于同一测试环境
下的前后对比，不代表所有硬件上的固定性能。

## 性能优化

自研 C++ SLAM 使用 `RelWithDebInfo` 作为默认构建类型，对应 GCC/Clang
常用的 `-O2 -g -DNDEBUG`。复现性能数据前应显式执行：

```bash
colcon build --packages-select slam_robot_slam slam_robot_slam_3d \
  --symlink-install \
  --cmake-args -DCMAKE_BUILD_TYPE=RelWithDebInfo
```

不要使用 `CMAKE_BUILD_TYPE` 为空的构建结果评估扫描匹配性能；这种情况下
GCC 默认等同 `-O0`。

| 处理耗时最大值 | 0.881 ms |

配置依次执行有限值、`0.25–20.0 m` 量程、本体包围盒和 `0.10 m` PCL

连续 1000 帧。

| 指标 | `0.10 m`（2026-08-05） | `0.05 m`（2026-08-11） | 倍数 |
| --- | ---: | ---: | ---: |

解释了为什么快照体积是 `2.7` 倍而非更高。耗时均值 `0.685 ms` 相对
`preprocessing_regression` 的 `10.0 ms` 判据仍有 14.6 倍余量，判定 PASS；该判据
是在约 `100 Hz` 输入压力下测的，在线传感器只有 `10 Hz`。

该结果覆盖结构化场景前 10.7 m，不代表闭环 SLAM 精度；当前没有回环或全局
后端。首版曾用 `0.05 s` 最近邻容差直接接受滞后的里程计，因此“没有同步

合成双平行墙测试的平移信息特征值比低于 `0.01`，而正常路段 P05 为
`0.1050`；默认诊断门限取 `0.05`。该门限用于识别弱方向，并由
`0.01–0.05` 双阈值连续控制该方向的 GICP 修正。

平行侧墙对横向位移和航向提供强约束，但中段没有可用于估计纵向位移的
几何结构。初版处理对最佳匹配附近的原始相关响应做二维有限差分，以响应
Hessian 的特征值判断平移可观测秩。秩为 1 时移除弱特征向量上的激光
修正，保留该方向的轮式里程计预测；横向和航向匹配不变。输出协方差沿
弱方向从 `0.05 m` 增大到 `0.30 m`。上表记录的是这版实现，其纵向峰值
相对未处理基线下降约 81%。

上表的 392 是激光里程计消息数，不是独立匹配次数：运动不足和拒配路径会
重复发布上一次协方差，因此不能用它推导退化检出率。加入逐次匹配诊断后，
同一默认配置再次执行 25 m 单向回归，共发生 314 次真实匹配，其中 rank 1
为 190 次、rank 2 为 124 次；在这次固定仿真中的检出比例为 60.5%，漏检
比例为 39.5%。ratio 直方图按边界
`[0, .01, .025, .05, .10, .25, .50, 1]` 的计数为
`[91, 29, 70, 94, 30, 0, 0]`。本次纵向峰值 / 最终误差为
`0.130 m / 0.080 m`，横向峰值为 `0.026 m`，无拒配或错误回环。

真实角采样单元测试使用与模型一致的 720 束、stride 2、12 m 量程，覆盖
1/5/20 个关键帧与 `0/0.0025/0.005/0.01 m` 测距噪声。12 种组合中旧版
响应曲面检测器给出 3 次 rank 1、9 次 rank 2；rank 1 时保留了准确的
`0.10 m` 里程计预测，rank 2 时结果被相关匹配拉回 `0.02～0.08 m`。
这说明处理在触发时有效，但响应 Hessian 会把光束端点混叠误当成沿走廊
方向的信息，且结果随子图深度与噪声变化。

当前实现改为在每帧扫描内部保留原始光束索引和量程，只在索引连续且
相邻点距离满足 `0.05 m + 0.05 × range` 的七点窗口中拟合局部直线法向。
归一化矩阵 `Σnᵢnᵢᵀ / N` 的特征值比表示两个平移方向的相对表面支撑，
未归一化特征值则直接表示有效法向数量。弱方向激光修正比例连续取
`min(1, ratio / 0.05)`，避免旧版 rank 硬切换。

上述 12 种组合在新检测器下全部为 rank 1，纵向估计相对准确的
`0.10 m` 预测最大偏差不超过 `0.011 m`，不再随子图深度翻转。最终验收的
25 m Gazebo 回归发生 314 次真实匹配，rank 1 / rank 2 为 `227 / 87`；端墙和
非对称入口/出口锚点可见时存在真实纵向法向，因此 rank 2 是预期结果，
中部长平行墙稳定为 rank 1。物理中段的 188 次真实匹配全部为 rank 1，
检出率 `100%`。本次纵向峰值 / 最终误差为 `0.133 m / 0.123 m`，横向峰值
`0.035 m`，最大前端间隔 `0.100 s`，无拒配或错误回环。正常场景的独立
闸门已加入长闭环和三档快速旋转回归，
两者分别覆盖 209 和 651 次真实匹配，均要求退化误报严格为零。

同一配置随后重复执行单向测试，纵向峰值分别为 `0.210 m` 和 `0.150 m`，
其余横向、航向、前端间隔和无错误回环判据均通过。因此自动回归使用
`0.25 m` 单向连续上限，在保留约 70% 以上基线改善要求的同时覆盖出口
锚点处约一个栅格的运行波动。

### 输入同步率测量

烟雾验收的 1 Hz 无法区分「每帧点云都完成同步」和「多数点云被同步器丢弃」，
因为 `Rtabmap/DetectionRate` 的限速发生在同步回调之后。为把两者分开，把
`Rtabmap/DetectionRate` 临时置 `0`（不限速），此时 `/rtabmap/info` 的发布率
等于同步回调率，可直接与点云率对比。

| 配置 | `/lidar_3d/points` | `/rtabmap/info`（不限速） | `/odom` |
| --- | --- | --- | --- |
| `approx_sync: false`（原配置） | `10.00 Hz` | `10.000 Hz` | `50.0 Hz` |
| `approx_sync: true`（当前配置） | `10.00 Hz` | `10.000 Hz` | `50.0 Hz` |

结论：**精确时间同步在本仿真中并没有丢帧**，回调率等于点云率。原因是
点云时间戳落在整 `100 ms` 栅格上（实测连续戳 `37.300 / 37.400 / 37.500 …`），
而 EKF 以 `50 Hz` 落在 `20 ms` 栅格上，两者恰好成整数倍关系，因此每个点云
时间戳都有一条时间戳完全相同的 `/odom`。

这是巧合而非设计保证：把 `ekf_2d.yaml` 的 `frequency` 改成 `30 Hz` 之类
不整除点云周期的值，或迁移到时间戳不落在公共栅格上的真实硬件，精确同步
会静默失效——表现为输入饥饿而不是报错。因此改用 `approx_sync: true` 并把
`approx_sync_max_interval` 设为 `0.02 s`（`50 Hz` 里程计最坏 `10 ms` 偏差的
两倍，且只有点云周期的 `1/5`，不会跨接到相邻扫描）。改动后回调率不变，
`Did not receive data` 警告为 `0` 次。

破坏闭环、地图契约或 1 Hz 实时预算。

运行命令：

```bash
ros2 launch slam_robot_slam_3d structured_loop_regression.launch.py
```

### 单圈回环不可靠的归因与 `ProximityPathMaxNeighbors` 反驳

2026-08-05 排查"单圈 proximity 约束时有时无"。原假设是
`RGBD/ProximityPathMaxNeighbors`（配置为 `1`）对稀疏 16 线点云过小。该
假设的两个前提都被推翻。

第一，参数语义理解有误。RTAB-Map 的默认值是 `0`，含义是**禁用** one-to-many
proximity 检测；配置里的 `1` 已经是启用状态，只是每条路径仅合并 1 个邻居
节点，合并后的目标扫描与单帧一样稀疏。

第二，真正的限制是路线几何，与参数无关。用固定包的真值轨迹按
`Rtabmap/DetectionRate=1.0` 与 `RGBD/LinearUpdate=0.10` 复现图节点插入
（模型 `329` 个，实测 `346` 个），再统计"路径距离相差 `20 m` 以上且欧氏
距离在半径内"的历史节点：

| 半径 | 第 1 圈有重访候选的节点 | 第 2 圈 |
| --- | ---: | ---: |
| `10 m`（`RGBD/LocalRadius`） | `18/160`（`11.2%`） | `169/169`（`100%`） |
| `3 m`（与扫描重叠相称） | `3/160`（`1.9%`） | `169/169`（`100%`） |

`72 m` 闭环跑一圈只在最后几秒进入已建图区域，能否命中取决于当时的累计
漂移，因此呈现全有全无的模式，而不是可以调参改善的连续量。

固定包回放前 `176 s`（第 1 圈）的 A/B：

| `ProximityPathMaxNeighbors` | proximity | `map -> odom` 峰值 | 图节点 |
| --- | ---: | ---: | ---: |
| `1` | `2` | `0.350 m` | `146` |
| `1`（另一次） | `3` | `0.870 m` | `171` |
| `10` | `6` | `0.685 m` | `148` |

单圈确实有提升，但绝对量仍是个位数，且三次运行 `loop_closure_id` 均为 `0`
（无相机、词袋禁用，符合能力边界）。回放并非完全确定性：`DetectionRate`
受实际调度影响，两次 `1` 的图节点数为 `146` 与 `171`。

真正要采用它的场景是两圈回归，结果是**没有收益**：

| 指标 | `1`（记录基线） | `10` |
| --- | --- | --- |
| 路线 | `143.1 m`，`8/8` | `143.1 m`，`8/8` |
| 图节点 | `347` | `347` |
| proximity 约束 | `181` | `185` |
| 航迹推算 / SLAM 误差 | `1.328 m` / `0.004 m` | `0.992 m` / `0.002 m` |
| `map -> odom` 峰值 | `1.369 m` | `1.042 m` |
| 栅格 | `28.00 x 16.15 m` | `28.00 x 16.15 m` |
| 自动判据 | 全部通过 | `17/17 PASS` |

`181 -> 185` 是 `2%`，而两次运行的航迹推算漂移本身就差了 `1.328` 对
`0.992 m`，该差异落在运行间噪声内。两圈几何已提供约 `2368` 对候选，瓶颈
不在合并扫描的稠密度，所以参数在这里不起作用。配置保持 `1`，不采用 `10`。

`10` 的代价在 1 Hz 预算内：`361` 帧 RTAB-Map 核心处理均值 `67.6 ms`、
P95 `126.4 ms`、最大 `144.4 ms`，无超过 `200 ms` 的帧。但没有同一套量法的
`1` 对照，因此不宣称 `10` 更快或更慢。

结论：单圈回环不是可以靠调参解决的问题。要做单趟即可验收回环的快速回归，
需要中途折返的路线（8 字形或带返回支路），属于世界设计任务。

### 高度语义 Nav2 自动回归

2026-08-04 在同一 `structured_loop_3d.sdf` 中加入两个互补靶标：

- 高门洞下沿 `0.55 m`，高于 `0.35 m` 机器人和 `0.45 m` 安全扫掠高度；
- 蘑菇柱底座半径 `0.07 m`，但 `z=0.18–0.44 m` 柱帽半径为 `0.40 m`。

`structured_navigation_regression.launch.py` 先执行原有两圈闭环建图，再由
Nav2 完成五个目标。门洞段记录真值穿越截面；柱帽段的直线会穿过粗柱帽，
脚本要求地图环带存在占据单元、机器人与柱心距离至少 `0.55 m`，且向走廊
内侧绕行至少 `0.25 m`。同时要求门洞中心在二维投影中保持自由。

首次完整运行结果：原有建图 `15/15` 判据通过，高度导航 `8/8` 判据通过，
五个 Nav2 目标全部到达。MPPI 在柱帽之后接近最终目标时出现一次
`Failed to make progress`，行为树清图并重新规划后成功完成；Collision
Monitor 没有导致任务失败。回归进程成功退出，结束后未发现残留仿真实例。

```bash
ros2 launch slam_robot_slam_3d structured_navigation_regression.launch.py
```

手动在线导航复测发现一条此前回归未覆盖的失效路径：RTAB-Map 默认允许六自由度
ICP，运行一段时间后实测 `map -> odom` 达到 `z=0.167 m`、横滚
`-0.71°`，而 `odom -> base_footprint` 仍严格为二维。这个小倾角足以让远处
地面返回越过 `0.05 m` 地面阈值；全局 PointCloud2 障碍层出现围绕机器人的
同心弧线，并把可通行走廊连成 `NO_VALID_PATH (208)`。

临时把地面阈值提高到 `0.10 m` 仍无法消除远距离倾斜误差，因此没有采用
“继续抬高过滤阈值”的掩盖方案。正式修复是启用 `Reg/Force3DoF=true` 与
`RGBD/ForceOdom3DoF=true`，保持三维点云地图但约束平面机器人轨迹；结构化
回归同时新增 `map -> odom` 高度峰值不超过 `0.02 m`、横滚/俯仰峰值不超过
`0.5°` 的硬判据。清空旧数据库后再次手动建图和导航，原先的地面同心弧假
障碍消失，蘑菇柱附近可正常规划和通行；完整自动长回归仍由上述新增判据持续
覆盖。

纯 LiDAR RTAB-Map 不依赖相机才能建图，但没有图像时视觉词袋回环与视觉重定位
被禁用，回环范围收窄为空间 proximity 预测加 3D ICP 验证。运行中的
`Missing visual features` 提示对应这一能力边界，不表示当前 LiDAR ICP 回环
失败；后续相机用于增强全局地点识别。

### EKF 周期裕度与一次测量方法教训

首次在导航链路上观察到 `7` 次 `Failed to meet update rate`（最长
`0.224 s`）并一度记为「叠加 Nav2 后的已知资源竞争」。复查后确认**这个
结论是错的，起因是测量环境本身被污染**：用于收尾的
`kill -INT <ros2 launch pid>` 并不会回收该 launch 的子进程树，于是先前
几次运行遗留的 Gazebo、RTAB-Map、EKF 和桥接进程一直在后台运行。故障
被发现时机器上同时存在 `5` 个 `gz sim` 实例和多个 `ekf_filter_node`，
系统负载 `55`。多个 EKF 同时向 `/odom` 和 `/tf` 发布，测到的超时是这些
互相竞争的实例造成的，与本项目的配置无关。

改用 `setsid` 让每次运行独占一个进程组、结束时按进程组整体回收，并在
每次运行后校验无残留进程，重新测量：

| 运行环境 | 时长 | EKF 周期超时 |
| --- | --- | --- |
| 污染环境（多实例并行） | — | `7` 次，最长 `224 ms` |
| 隔离运行，静态 DDS 图 | `90 s` | `0` 次 |
| 隔离运行，反复起停 `ros2` CLI 进程 | `44 s` | `0` 次 |
| 隔离运行，全程 | `137 s` | `1` 次，`24 ms` |

隔离后唯一一次超时是 `24 ms`（目标周期 `20 ms`，超出 `4 ms`），发生在
驱动进程加入 DDS 图的瞬间。**完整 Nav2 + RTAB-Map + Gazebo 链路在本机
留有充足的 EKF 周期裕度**，不存在需要整改的资源竞争。

留下的教训与 SLAM 本身无关但会反复出现：`ros2 launch` 在非交互 shell
中被后台执行时，向其 PID 发 `SIGINT` 不足以终止整棵进程树；一个泄漏的
仿真实例足以在不报任何错的情况下让后续所有时序测量失真。现有回归脚本
（如 `corridor_regression`）是由 launch 文件拉起的 ROS 节点，由 launch
系统负责回收，不受此影响；受影响的只是手工用 shell 拉起仿真的临时测量。

### 探索覆盖与栅格投影整改

上表的自研首次结果（26,334 个自由单元、14.019 m）保留为整改前历史记录，不能
再作为“探索充分”的验收依据。此前二维投影会直接丢弃高度带外的地面回波，导致
它们既不形成障碍也不提供自由空间证据；同时每十个关键帧都会从零重放全部历史
扫描。现已改为地面回波仅提供自由射线、导航高度带内回波提供命中，并在非回环
时增量整合新关键帧；位姿图校正和快照恢复仍执行分批全量重建。

回归门槛取 RTAB-Map 同场景结果的一半：`38,000` 已知自由单元和 `35 m` Gazebo
真值行程，旧结果会明确失败。整改后同一入口完整通过：4 个目标成功、1 个失败
目标进入黑名单、探索完成并成功保存快照；运行中已知自由单元超过 42,000。评分器
还要求完成消息属于本次运行，并将“快照服务不可用/请求失败”视为关键错误。

**这两个数字是防退化闸门，不是目标性能，也不构成两条链路的公平对比结论。**
42,000 / 76,012 ≈ 55% 只说明端到端行为达到了最低护栏。差距不能归因于探索时长：
本次自研运行在约 185 s 就主动发布 `complete=true`（上限 600 s），是在自己的
`/map` 上找不到可达 frontier 而停的，把上限提到 900 s 不会让它多探索。

55% 只是**本次运行的结果**。它由地图投影还是探索策略造成，用下面的固定包对照
分离。

### 墙被当成 frontier：三态投影的第二次分类错误

上面的六次重复运行只是把主机因素分离出去。继续重复运行后，出现了一次主机完全健康
的核心失败：地图形状正常、覆盖达标（76,077 自由单元），但机器人跑满 `900 s` 未收敛，
真值行程 `315.978 m`（其余运行 100–182 m）。

`frontier_explorer` 的事件时间线把预算去向说清楚了：

| 阶段 | 时间 | 行为 |
| --- | --- | --- |
| 探索 | 0–248 s | 8 个目标，得分 117 → 1.14，覆盖完成 |
| 空转 | 248–626 s | **三次导航超时，每次耗满 `120 s`** |
| 抖动 | 626–900 s | 8 个目标在数秒到数十秒内被判不可通行取消 |

三次超时占 `900 s` 预算的 **41%**，而 7 次有效目标只用了约 `248 s`。这些目标的位置
与世界几何对得上：`inner_north` 墙中心 `y=10.5`、厚 `0.2`，外面在 `y=10.6`，而超时
目标是 `10.68 / 10.68 / 10.58`；`inner_south` 外面在 `y=1.4`，抖动阶段目标是
`1.43 / 1.38 / 1.38`。机器人半径 `0.22 m`，这些目标落在墙面几厘米内甚至墙体内部。

`frontier.minimum_clearance: 0.25` 没有拦住它们，因为净距是按已发布地图中
`value >= occupied_minimum` 的格子算的。而三态转换把证据不足的墙格发成 `-1`，于是
墙对净距变换不可见，同时相邻自由格满足"自由格紧邻未知"——**墙本身成了探索目标**。

这与最初那次 frontier 被遮蔽是同一个机制的两个方向：中间桶里混着"从未观测"和
"部分观测的障碍"，前者该去探索，后者是障碍。RTAB-Map 用单一
`GridGlobal/OccupancyThr = 0.5` 消除了这个桶，其 `ProbHit/ProbMiss` 与本仓库相同
（`0.7/0.4`），因此它的投影里不存在中间值单元，本仓库先前实测为 1,427 个。

### 固定包 A/B：两项改动的正交分解

整改为两项：`occupancy_grid.occupied_minimum` 由 `65` 降到 `50`，让证据净偏向占据的
已观测格发成障碍；`occupancy_grid.maximum_ray_range` 限定进入二维投影的回波距离，
前端仍使用完整 `20 m` 点云。用同一份固定包回放做 2×2 参数对照：

| 配置 | 自由 | 占据 | 未知 | 已知包围盒 |
| --- | ---: | ---: | ---: | ---: |
| `20 m` / `65`（原） | 75,534 | 3,531 | 86,007 | 404.3 m² |
| `20 m` / `50` | 75,534 | 3,773 | 85,765 | 404.3 m² |
| `8 m` / `65` | 75,182 | 3,835 | 84,667 | 400.8 m² |
| `8 m` / `50`（现） | 75,182 | 4,077 | 84,425 | 400.8 m² |

两项正交：阈值只动占据侧（同一距离下自由格逐位相同），距离只动覆盖范围。合计占据
`+15.5%`、未知 `-1,582`、自由 `-0.5%`。

其中**距离是主项**（`+304` 占据格，阈值为 `+242`），且方向反直觉：积分的回波变少，
占据证据反而变强，说明远距掠射射线此前沿墙面记 miss、在侵蚀墙体证据。覆盖代价
`-0.5%`，与 RTAB-Map 用默认 `Grid/RangeMax = 5.0 m` 取得同等覆盖一致。

### 偶发的地图全局拉伸（成因见下一节）

多数运行的地图边界精确贴合外墙面，四边越界均为 `0.000 m`（整改前 2/10、整改后
3/10、验收 4/10 为全零，其余多在厘米级）。但整改前后各出现过一次量级完全不同的
外扩，以整改后那次为例：

| 边 | 越界 |
| --- | ---: |
| west | 0.000 m |
| south | 0.750 m |
| east | 0.400 m |
| north | 0.850 m |

南北同时外推、合计 `1.60 m`，正好解释该次高度从约 `15.0` 涨到 `16.80 m`。**南北同时
外推是全局拉伸的特征，不是单侧墙体涂抹。**该次的真值行程、目标数、位姿图提交、接受
回环数和前端子图重启全部居中，与其余九次无异，因此现有诊断解释不了它，其量级上界也
无从推断。

它不造成判据失败，只消耗包围盒余量；`17.5 m` 的高度上限覆盖了实测的 `16.80 m`，且
相对畸变形态的 `20.10 m` 仍有判别力。四边越界诊断按边分别记录正是为下一次复现时定位
用的：典型运行为精确的 `0.000 m`，这个信号足够干净。

### 成因：地图按轮速里程计而非扫描匹配位姿重建

上面缺的是一个能定性的测量。探索回归此前完全不检查轨迹精度，只用地图包围盒当代理，
而包围盒无法区分"位姿错了"和"位姿对但投影把地图拉开了"。补上两个位姿对真值的误差
统计后，一次运行就把问题指了出来：

| | 前端位姿误差 | 地图系位姿误差 | 倍数 |
| --- | ---: | ---: | ---: |
| 五次运行 | `0.016–0.031 m` | `0.190–2.717 m` | 7–88 |

前端指 `/custom_slam_3d/laser_odom`，即 GICP 自身的估计；地图系指 TF
`map -> base_footprint`，即 Nav2、探索器和地图重建实际使用的位姿。两者从不相遇：

- 优化前缀之外的关键帧用 `map_from_odom_ * odom_base_pose` 放置，丢掉了同一结构体
  里的 `front_end_base_pose`；
- `map_from_odom_` 只在位姿图提交时更新，而提交只在接受回环时发生
  （`PoseGraphSubmissionState::begin()` 在 `pending_constraints_` 为空时直接返回）。

单趟探索常常一个回环都没有。一次实测运行 `5,730` 个检索候选全部被描述子门限拒绝、
`proposals=0`、提交 `0` 次，于是整张地图按裸里程计绘制：地图系位姿误差 `2.717 m`、
越界合计 `2.600 m`，而同一时刻前端对真值的误差是 `0.031 m`。这解释了先前记录的全部
特征——`west` 越界为零（起点漂移为零）、南北同时外推（漂移随行程累积）、与回环数弱
相关（回环越少，优化前缀越短）、与前端指标无关（前端不在这条路径上）。

修正所需的量后端早已算好而节点从未使用：
`map_from_local = optimized_latest * front_end_base_pose.inverse()`。现在未优化关键
帧按 `map_from_local_ * front_end_base_pose` 放置，`map -> odom` 也每帧经同一修正量
重算，因此两次优化之间消费者跟随的是扫描匹配而非裸里程计。两处同源派生，且都不增加
计算量。

### 修正后的对照

| | 前端位姿 | 地图系位姿 | 比值 | 越界合计 |
| --- | --- | --- | ---: | --- |
| 修正前（5 次） | `0.016–0.031 m` | `0.190–2.717 m` | 7–88 | `0.000–2.600 m` |
| 修正后（10 次） | `0.012–0.074 m` | `0.012–0.091 m` | 0.97–1.23 | 全部 `0.000 m` |

最直接的证据是同场景对照：两次运行同为零回环、前端误差同为 `0.031 m`，修正前地图系
误差 `2.717 m`、越界 `2.600 m` 且判失败；修正后 `0.030 m`、越界 `0.000 m` 且通过。
这是对被修对象的直接测量，不依赖通过率统计。

修正后批次 `10/10` 通过，无核心失败，无主机归因。据此把地图系位姿误差纳入核心判据：
上限 `0.30 m` 与 `1.50°`，约为实测上限的 3.3 和 5.7 倍，同时相对失效样本的 `2.717 m`
与 `13.285°` 保留约 9 倍判别余量。

一个副产品值得记：修正后误差最大的一次（前端 `0.074 m`）地图系为 `0.091 m`，仍然贴合。
**修正后地图质量的上限由前端精度决定**，这正是应有的关系；修正前则是前端好而地图任意
差，两者脱钩。

### 存档恢复的端到端首次验收

在此之前，恢复路径只有单元覆盖，没有任何入口跑过“存档 → 重启 → 继续建图”。
2026-08-11 用 `structured_3d_reference` 在第 `240 s` 切开：前段建图并经
`~/save_snapshot` 保存，后段以全新前端 `load_snapshot:=true` 从 `--start-offset 240`
放完余下 `121 s`。

| 指标 | 前段（0–240 s） | 后段（240–361 s） |
| --- | ---: | ---: |
| 地图系峰值误差 | `0.019 m` / `0.099°` | `0.022 m` / `0.107°` |
| 地图系配对样本 | 11,946 | 6,070 |
| 位姿图提交 / 丢弃 / 异常 | 4 / 0 / 0 | 6 / 0 / 0 |
| 全局关键帧 | 393 | 393 → 581 |
| 已知栅格 | 79,247 | 恢复出 79,260 |
| 快照 | `22,082,781 B` | — |

**接缝峰值误差 `0.0184 m` / `0.0816°`**，比前段自身峰值还小。这是本次要证的那一条：
恢复后的位姿落在保存时的同一个地图系里，重启没有引入跳变。度量方式是关键——后段
用的是**前段写进报告的锚点**；若照本仓库其它判据的做法各自锚到自己的第一帧，落在
错误位姿上的一整段会把跳变吸收进新原点，测出零误差。

连续两次运行的复现性很高：接缝位置误差两次均为 `0.018363 m`，关键帧同为 `393 → 581`，
提交同为 `4 / 6`；只有偏航峰值在 `0.067°` 与 `0.082°` 间浮动，取决于哪些样本配对成功。
通过的那次两段报告存于 `docs/results/2026-08-11-snapshot-resume.json`。

阈值据此设定：接缝 `0.10 m` / `0.50°`（约实测的 5 和 6 倍），峰值增长 `0.05 m` /
`0.30°`（实测增长为 `0.003 m` / `0.008°`，取值刻意更松，因为两个峰值之差比峰值本身
抖动大）。相对被防的失效——恢复到错误坐标系会整体偏移一个累积修正量，量级在米——
仍保留两个数量级的判别余量。

过程中有三件事值得记，因为它们都不是“跑一遍就对”的：

- **`--split 180` 判 FAIL，但代码没问题。** 包的前 180 s 是第一圈，零回环、零提交，
  保存下来的坐标修正是单位阵，重基准等于没做。判据里那条“保存前必须有提交”正是为此
  存在：它拒绝报一个没挣到的 PASS，并提示改 `--split`。
- **`/tf_static` 在包里只有一条、位于开头**，`--start-offset` 会跳过它。现象极具
  迷惑性：恢复成功、地图发布正常，然后前端一帧扫描都不处理，一直等 `lidar_3d_link`。
  先试的“再起一个只放该话题的播放器”不可靠——它发布后 1 s 内就退出，transient_local
  的发布者在发现完成前消失，实测无人收到。改为从包里读出该消息并常驻广播
  （`recorded_static_tf_publisher`），把竞态消除而不是缩窄。
- **“已知栅格必须增长”是错的判据。** 这个包是同一环路两圈，后段走的是已建过的区域，
  没有新面积；已知栅格也本就不单调（落入自由与占据之间那条带的格子会重新发布为 −1）。
  实测 79,260 → 79,227，抖动 33 格。改为要求关键帧增长、地图持续发布、已知栅格不塌陷；
  覆盖增长这个数据集给不了，就不拿它当证据。

### 完成判定的事后核对与双栈栅格对照

2026-08-11 一次手动探索运行在 `3 分 18 秒` 后自主判完成（`no reachable frontier
remains`，5 个目标全部成功、0 失败），但地图上有一个圆柱障碍的轮廓看起来没有闭合。
下面是事后核对：加载该次运行留下的快照（234 个关键帧）重建 `/map`，再按 frontier
检测器自己的门限逐格复算。方法本身值得记——**快照使终态地图可逐格复现，不必重跑仿真**。

复算结果：全图 479 个 frontier 格（自由格紧邻未知格），8 连通聚类 194 簇。

| 格数 | 最大 clearance | 中心 | 按 `minimum_cluster_cells=8` / `minimum_clearance=0.25` 判定 |
| ---: | ---: | --- | --- |
| 19 | `0.224 m` | (−3.14, −2.61) | clearance 不足 |
| 9 | `0.255 m` | (0.40, 3.64) | **通过** |
| 8 | `0.112 m` | (0.04, −4.88) | clearance 不足 |
| 其余 191 簇 | ≤`0.16 m` | | 全部不足 |

那个圆柱的 frontier 簇只有 `7` 格和 `5` 格，两道门限各差一大截。实心柱内部本就不可
观测，`1` 格宽的轮廓缺口属于标记采样问题。**全图任何一个 frontier 格的最大 clearance
只有 `0.255 m`**——没有任何一个开阔边界残留，完成判定成立。唯一够格的候选在三项上
都卡在门限边缘（9 vs 8、`0.255` vs `0.25 m`、`0.255` vs 机器人半径 `0.22 m`），
被路径规划筛掉不计入 `failed goals`，因此 `no reachable frontier` 的措辞是准确的。

同一世界上另有一次 RTAB-Map 探索（`3 分 05 秒` 后手动中断，未自主完成），其数据库
经 `/rtabmap/get_map` 取出后用同一段代码复算。**两次运行完成度不同，不能比"谁更
完整"；但探索器与门限完全相同，比地图质量是公平的**：

| | RTAB-Map（中断） | 自研（自主完成） |
| --- | ---: | ---: |
| 栅格范围 | `13.05 × 11.00 m` | `12.10 × 10.10 m` |
| **自由格** | **43,688** | **43,867** |
| 占据格 | 2,754 | 1,991 |
| 未知格 | 10,978 | 3,026 |
| frontier 格 | 360 | 479 |
| 通过双门限的簇 | 0 | 1（边缘） |
| 任意 frontier 最大 clearance | `0.112 m` | `0.255 m` |
| 未知连通域 | 24（其中 `<4` 格：**5**） | 130（其中 `<4` 格：**120**） |
| 障碍内部封闭块（≥4 格） | 18 | 9 |

三条结论：

**一、可通行区域几乎一致。** 自由格 43,688 vs 43,867，差 `0.4%`。两条独立管线在同一
世界圈出的自由空间是同一块，这是目前最直接的等价证据。

**二、自研的障碍标记明显更稀。** 占据格少 `38%`，封闭障碍块 9 vs 18。成因是投影只取
`0.05–0.45 m` 这条 `0.40 m` 宽的带：16 线 LiDAR 在 `8 m` 处相邻线已差 `0.28 m`，某个
扇区若只从远处掠过，可能没有一根线落进带内。实测一堵 `3.6 m` 的墙上沿几乎实心、
下沿约一半是洞。单次命中即可标为占据（`hit_probability 0.70` 一次到 70 > `occupied_minimum
50`），所以问题是"没有光束落在带内"，不是"命中次数不够"；这种缺口也不会被擦除，
因为能把该格标自由的射线必须终点在障碍之后。

导航上目前没有危害：`robot_radius 0.22 m` 配 `inflation_radius 0.70 m`，`0.30 m` 厚的
墙内部整个落在 inscribed 半径内被标致命，规划器穿不过去（尽管 `allow_unknown: true`、
`track_unknown_space: true` 本身允许走未知格）。**兜底的是膨胀层，不是地图。** 但它
确实影响 frontier 检测：稀疏的占据格会抬高 clearance 变换的取值，而 clearance 正是
检测器的可达性代理——上表那个 `0.255 m` 的边缘候选就是这么来的。

**三、约 120 个孤立未知斑点是自研独有的，源于双门限设计。** RTAB-Map 用单门限
`GridGlobal/OccupancyThr 0.5`，每格非自由即占据，不存在中间态；自研用 `25 / 50` 双
门限，落在中间带的格子发布为 −1。按对数几率算，`miss_probability 0.40` 一次得 40、
两次得 31、三次得 23——**恰好被观测两次的自由格会落在 26–49 带内而发布为未知**。
这些斑点零散分布在自由空间里，每个都制造几个假 frontier：

| | 未知格 | frontier 格 | frontier / 未知 |
| --- | ---: | ---: | ---: |
| RTAB-Map | 10,978 | 360 | 0.033 |
| 自研 | 3,026 | 479 | **0.158** |

**自研未知格只有 RTAB-Map 的 27%，frontier 格却多 33%**，单位未知量产生的边界是
`4.8` 倍。194 簇平均只有 `2.5` 格，全部被 `minimum_cluster_cells: 8` 拦下，因此本次
没有造成误判——但拦住它的是一道下游过滤器，而不是干净的源头。

据此的处置结论见下节。

### 上述两项是否需要改：结论是先测量、不动参数

涉及的四个参数——`free_maximum 25`、`occupied_minimum 50`、高度带 `0.05–0.45 m`、
`maximum_ray_range 8.0`——全部来自已完成的标定活动，且互相牵制：

- 抬高 `free_maximum` 能让"两次 miss"的格子归为自由，消掉多数斑点，但它同时放宽了
  倾向占据的格子被判自由的条件，正是安全方向上的让步。
- 放宽高度带或量程门能补上障碍轮廓，但 `0.45 m` 上限是为保留高门洞、挡住上部外扩
  障碍而定，`8.0 m` 量程门则是"墙被当成 frontier"那次整改的直接产物。

也就是说，任何一项调整都会重新打开一个已经用三十次运行关闭过的问题，必须重跑整个
活动才能证明没有退化。而目前**没有观测到实际危害**：自由空间两栈一致，规划未受影响，
斑点从未形成通过门限的簇，唯一通过的候选来自轮廓缺口且仍被规划筛掉。

因此建议：

1. **不动上述四个参数。**
2. **把这两项变成被跟踪的数字，而不是轶事。** 在探索回归的报告里增加三项廉价指标：
   孤立未知格数（`<4` 格的未知连通域数）、占据格数、`frontier 格 / 未知格` 比值。
   本次的 120、1,991、0.158 可作为首版基线。指标一旦变化就会被回归抓到，届时再改
   参数才有依据。
3. **在配置里写明 `minimum_cluster_cells` 正在承担的实际职责。** 它现在挡的是投影
   噪声，而不只是"太小的边界不值得去"，这一点原注释没有体现；承重的东西必须写明，
   否则下一个人会以为它可以随手调小。

只有当孤立斑点真的凑出一个通过双门限的簇时才动手，且那时的正确方向多半是形态学
处理（未知格需成簇才发布为 −1），而不是移动门限——移动门限会把问题推回另一边。

### 双分辨率点云与占据轮廓 A/B

2026-08-11 用 `structured_3d_reference` 全长 `361.6 s` 固定包做对照。两次均使用
相同的 `0.10 m` GICP 注册体素、占据高度带、射线距离、概率门限和位姿图参数；
主变量是占据投影的输入体素：旧链路 `0.10 m`，新链路 `0.05 m`。新链路没有增加
第二个 ROS 话题，而是在前端内部从同一 `0.05 m` 消息派生注册点云。

**严格说这不是单变量对照**：注册点云的生成路径也变了，从"原始 → `0.10 m`"变成
"原始 → `0.05 m` → `0.10 m`"，级联体素化的体素质心与一次体素化并不相同。下面
的前端指标（P95 `25.345 ms` 对历史 `25.257 ms`，最终误差 `0.012 m` 对 `0.010 m`）
说明这个次级变量的影响落在运行间波动内，因此不影响占据格的结论；但两次运行
差在哪里必须写准，不能笼统称作"唯一变量"。

| 指标 | 单分辨率 0.10 m | 双分辨率 0.05/0.10 m | 变化 |
| --- | ---: | ---: | ---: |
| 最终自由格 | 75,204 | 75,195 | −0.01% |
| 最终占据格 | 4,053 | 4,219 | **+4.10%** |
| 全局关键帧 | 580 | 580 | 0 |
| 3D 全局地图 | 38,538 点 | 38,607 点 | +0.18% |

结果说明新增样本主要补充了障碍端点，没有通过膨胀换取占据格，也没有收缩自由
空间。提升是温和的：它修正了 0.10 m 预体素化造成的部分稀疏，但 16 线雷达本身
的角采样仍是轮廓上限，不能据此宣称已达到 RTAB-Map 的全部地图质量。

同一配置随后通过完整回环回归：2,999 个样本接受率 100%，前端 mean/P95
`15.765/25.345 ms`，493 个关键帧、7 次图提交、0 丢弃/失败，最终位置/航向误差
`0.012 m / 0.020°`。因此内部二次体素化没有消耗 100 ms 扫描周期裕量。

持久化格式升级到 v3，每个关键帧保存注册和占据两份不可变点云；v1/v2 一律拒绝，
节点 FATAL 退出而不降级。这是取舍不是必然：旧文件那份 `0.10 m` 点云本可同时充当
两份，恢复出的占据栅格与改造前逐格相同，只是精度停留在旧水平。选择拒绝是因为
项目没有外部使用者、存量快照只有个位数，为此长期维护兼容分支不划算；代价是升级
即作废全部已有快照。第一版 v3 将所有 8 m 内占据输入都写入，393 帧为
`60,268,901 bytes`；实测其中 42.62% 的占据点高于 `0.45 m`，栅格重建必然跳过。
统一证据分类后只保留地面自由射线和高度带内障碍点，同一 393 帧生产快照降到
`44,049,718 bytes`，减少 **26.91%**，相对旧单云格式 `22,082,781 bytes` 的
倍率由 2.73× 降至约 2.00×。恢复后 393 → 581 帧，已知格 79,419 → 79,440，
接缝峰值 `0.019 m / 0.062°`，两阶段位姿图均提交且 0 丢弃/失败。

v3 同时持久化占据投影契约：`0.05 m` 输入体素、`0.05–0.45 m` 高度带、`8.0 m`
射线距离和强制平面运动。恢复时与当前参数逐项比较，不允许把按旧范围裁过的历史
点云静默用于新范围。非平面模式不做提前高度/距离裁剪，因为未来优化姿态可能改变
点在投影平面中的高度和距离。

随后在 `structured_loop_3d.sdf` 上完成一次从空地图开始的自研 SLAM + Nav2 +
Frontier Exploration 在线验收。探索器在 `321.8 s` 墙钟内自行以
`no reachable frontier remains` 收敛，12/12 个目标成功，真值行程 `80.319 m`；
最终自由格 `75,131`、自由面积 `187.828 m²`，已知边界
`26.90 × 14.90 m`，相对世界外墙四个方向的越界均为 `0.000 m`。前端位置峰值
`0.019 m`，地图系位置/航向峰值 `0.020 m / 0.127°`，0 碰撞、0 Nav2 恢复、
0 子图重初始化，回归结论为 `VERDICT PASS`。这说明双分辨率点云不仅改善固定包
中的障碍端点密度，也保持了在线地图、导航和探索的闭环契约。

该次回归在所有结果和 v3 快照成功写出后，Gazebo 与 `ros_gz_bridge` 仍于退出
清理阶段返回 `-11`。这是既有的仿真收尾问题，不计入上述算法验收，也不据此
宣称已经解决 Gazebo 进程稳定性。

### 随机化近优目标选择的活动验收

探索器改为在评分接近最佳的可达候选中随机选择后，原有的活动门限全部是在确定性
选择下标定的，因此必须重跑。2026-08-11 在 `structured_loop_3d.sdf` 上跑满
`10` 次，结果 **`ACCEPTED`，10/10 可评估运行通过，0 次归因主机**。

| 指标 | 最小 | 最大 | 均值 | 门限 | 余量 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 完成墙钟 | `256.8 s` | `360.8 s` | `304.4 s` | `900 s` | 2.5× |
| 最终自由格 | 75,117 | 75,331 | 75,206 | ≥42,000 | 1.79× |
| 真值行程 | `62.9 m` | `95.0 m` | `78.3 m` | — | — |
| 地图系位置峰值 | `0.020 m` | `0.031 m` | `0.024 m` | `0.30 m` | 9.7× |
| 地图系航向峰值 | `0.099°` | `0.173°` | `0.129°` | `1.50°` | 8.7× |
| 前端位置峰值 | `0.019 m` | `0.046 m` | `0.026 m` | — | — |
| 已知包围盒高 | `14.900 m` | `14.950 m` | `14.915 m` | ≤`17.5 m` | 1.17× |
| 规划器饥饿 | `0.00/min` | `0.21/min` | — | `0.60/min` | 2.9× |
| 墙外越界（四向最差） | `0.000 m` | `0.000 m` | — | — | — |
| 子图重初始化 | 0 | 0 | — | 0 | — |

目标计数为成功 `9–13`、失败 `0–1`、不可达 `0–1`；位姿图提交 `0–3`（单趟探索
常常不闭环，与既有记录一致）。全部 10 次 `host_healthy=yes`。**原有门限在随机化
之后仍然成立，且最紧的一项也留有 1.17 倍余量。**

最值得记的是两个离散度的对比：

| | 跨 10 次的分布宽度 |
| --- | ---: |
| 真值行程 | **51%**（62.9 → 95.0 m） |
| 最终自由格 | **0.28%**（75,117 → 75,331） |

**路线变化很大，覆盖结果几乎不变。** 但**这个离散度不能归因于随机化**：回归入口对
每次运行都传同一个 `exploration_seed:=20260811`，10 次的种子完全相同，日志逐条可查。
同种子、同策略之下仍有 `51%` 的行程差异，来源是仿真本身的非确定性（Gazebo 物理步进
与 ROS 调度时序），不是选择规则。它能说明的是另一件事：这批的通过不是靠"每次重复
同一条已知可行轨迹"换来的。

为了让这类问题以后能离线回答，探索器现在把每次决策的**全部候选**写进运行日志和
诊断：`FRONTIER SELECTION` 一行给出决策序号、候选数、池大小、名次和种子，随后每个
候选一行 `FRONTIER CANDIDATE`，带 `score` 及其全部分量（`gain`、`clearance`、
`distance`、`path`、`cells`）和是否被选中。记分量而不只记分数，是因为要回放的不只
是选择规则（top-k、softmax、不同带宽），还包括不同的评分权重。首批实跑样例：

```text
FRONTIER SELECTION decision=1 candidates=5 pool=1 rank=1 chosen_score=35.140
  scores 35.140 / 11.912 / 7.396 / 3.706 / 2.578      最佳领先 3 倍，随机化不参与
FRONTIER SELECTION decision=2 candidates=3 pool=2 rank=2 chosen_score=6.559
  scores  6.906 /  6.559 / 0.559                      前两名差 5%，随机选中第 2 名
```

`decision=2` 同时显示了代价：中选候选 `path=8.576 m`，落选的那个 `6.310 m`——多走
`2.3 m`。这类代价此前无法测量。

随机化的实际触发率比预期低得多。全批 114 次目标选择的候选池大小分布为：

| 池大小 | 1 | 2 | 3 | 4 |
| --- | ---: | ---: | ---: | ---: |
| 次数 | **100** | 11 | 2 | 1 |

也就是 `88%` 的决策点只有一个候选落在最佳分数的 `20%` 带内，随机化根本不参与；
上面那 `51%` 的行程差异，是由剩下 `12%` 的分歧点放大出来的。这一点对判读很重要：
不能把"随机化"当成每次都在大幅改变策略，它只在少数势均力敌的岔口起作用。

### 选择规则的离线回放对照

有了逐次决策记录，换一条选择规则不必再花一小时活动。`frontier_selection_replay`
读运行日志里的 `FRONTIER SELECTION` / `FRONTIER CANDIDATE` 行，对同一批真实决策
算出各规则的触发率与代价。2026-08-11 采集 3 次运行、`37` 次决策（每次 1–5 个可达
候选，上限由 `evaluation_candidate_limit: 5` 决定）：

| 规则 | 触发率 | 有效候选数 | 每次多走 | 每单位触发的米数 |
| --- | ---: | ---: | ---: | ---: |
| band `0.20`（现行） | 0.014 | 1.027 | `-0.003 m` | — |
| band `0.35` | 0.128 | 1.297 | `1.767 m` | 13.77 |
| band `0.50` | 0.160 | 1.378 | `1.734 m` | 10.84 |
| band `0.70` | 0.417 | 2.027 | `3.820 m` | 9.17 |
| top-2 | 0.486 | 1.973 | `5.422 m` | 11.15 |
| top-3 | 0.649 | 2.946 | `6.143 m` | 9.47 |
| softmax `T=1` | 0.052 | 1.220 | `0.692 m` | 13.30 |
| softmax `T=2` | 0.129 | 1.575 | `1.506 m` | 11.67 |
| softmax `T=4` | 0.260 | 2.220 | `2.914 m` | 11.20 |
| softmax `T=8` | 0.428 | 3.006 | `4.737 m` | 11.08 |

三条结论：

**一、现行 `band 0.20` 实际上等同贪心。** 37 次决策里只有 1 次候选池大于 1，触发率
`0.014`。上一节那 `51%` 的行程离散度，就是由这个量级的触发率经下游放大出来的。

**二、按触发率配平后，band 与 softmax 的代价接近，但买到的东西不同。**

| | 触发率 | 有效候选数 | 每次多走 |
| --- | ---: | ---: | ---: |
| band `0.50` | 0.160 | 1.378 | `1.734 m` |
| softmax `T=2.5` | 0.164 | **1.749** | `1.877 m` |

换算成"每多走一米买到多少额外目的地多样性"（超出 1 的有效候选数除以多走米数）：
band 为 `0.218`，softmax 为 **`0.399`**——**softmax 每米买到的多样性是 band 的
`1.83` 倍**。band 的随机化集中在两个相邻候选之间反复，softmax 把同样的概率摊到
多个不同目的地上；"别每次走同一条路线"要的是去不同的地方，不只是偶尔不选第一名。

**三、top-k 明显最差**，它完全无视分数差距：触发率 `0.486` 时每次多走 `5.422 m`，
是同触发率 softmax 的近两倍。

还有一条不在数字里但同样重要：**band 是硬阈值，代价随参数非单调**——`band 0.35`
的触发率低于 `0.50` 却更费路（`1.767` vs `1.734 m`），因为放宽阈值有时恰好放进一个
路径更短的候选。softmax 的各项指标随 `T` 单调平滑，调参行为可预测。

回放只回答逐次决策的问题。**一旦某规则选了不同目标，机器人就去了别处，后续记录
全部失效**，因此整趟行程、覆盖和完成时间的对比仍然只能靠真跑。

**这一批不是单变量对照。** 相对上一次活动，它同时包含双分辨率点云、随机化选择和
"顶部区间改为相对最佳分数而非最佳—最差跨度"三处改动，因此它验证的是当前配置整体
可接受，不能用来单独归因随机化的影响。要做归因需要另跑一批
`selection_top_score_band_fraction:=0.0`（退化为确定性选择）的对照。

逐次原始记录见 `docs/results/2026-08-11-randomised-selection-campaign.json`。

### 随机化到底买到了什么：种子对照与路线比对

前面几节把"路线多样"当成随机化的产出，这一节把它测了，结论是**没有买到**。

**一、换种子不改变结果分布。** 现行 band `0.20` 不动，改成每次运行抽新种子，跑 5 次
（`5/5 ACCEPTED`），与固定种子的 10 次并列：

| 指标 | 固定种子 ×10 | 新种子 ×5 |

## 2026-08-12：出生采样与依赖故障归因的整改

上面那批暴露的不是结果问题，而是**证据与归因的问题**。按顺序做了七项改动，每项
都改变了固定 seed 的位姿，因此期间不跑正式 campaign。

**记录**。采样器原本只输出世界、种子、分辨率、安全格数与位姿；决定位姿的其余
参数（机器人外接圆、平面余量、整机高度、垂直余量、最小间距、参考点、栅格上限）
一个都没记。上一批之所以能复现，是因为复核者恰好用了默认值，而不是因为知道它们。
现在整条记录是 `schema_version: 3` 的一行 JSON（经 nlohmann 生成），另含
`world_parsing_policy`、`world_geometry`、`support_resolution` 与 `sampling_bounds`；
campaign 追加 `source_revision`（commit 与 dirty 标志）。**后者是定位源码的线索
而非复现保证**：C++ 节点从 `install/` 运行，构建时间早于运行时间。

**Nav2 故障归因**。原实现第一次 goal 被拒即永久中止。Nav2 在 `on_configure`
就创建 action server、`on_activate` 才开始接受，所以图上可见的服务器会在整个
生命周期窗口内拒绝一切——探索器可能仅因为到得早就报废整轮。改为三段式：有地图、
有位姿、有可达 frontier 之后才开始计预算（否则等于把 SLAM 初始建图算到 Nav2
头上）；预算内的拒绝一律是重试，不拉黑候选也不计失败目标；只有超出预算才是故障。
预算用 `steady_clock`——这个机制要抓的依赖同时也是发布 `/clock` 的那个。

“就绪”改为**NavigateToPose 曾被接受**，而不是服务器出现在图上：planner_server
与 bt_navigator 独立激活，路径请求被接受说明不了导航目标会被接受。这条区分正是
`nav2_startup_timeout` 与 `nav2_runtime_lost` 的判据。故障以闭集字段
`failure_class` / `failure_code` 传播，回归在读取任何普通检查**之前**先答复它：
依赖失效时每一项检查都会因为地图不再产生而失败，而核心失败是先判的，否则整轮会
被记成算法回归。未识别的类别仍落回核心失败——这是安全方向。

**故障注入**。上述三环各有单测，但三个单测全通过也不能说明它们互相接通，而健康
运行永远走不到这条路径。因此实跑两条端到端场景：

| 场景 | 注入方式 | 墙钟 / 预算 | 判定 |
| --- | --- | ---: | --- |
| 启动期不可用 | Nav2 停在 configured 不 activate | `48.8 / 300 s` | `nav2_startup_timeout`，`INFRA_UNSTABLE` |
| 运行期丢失 | 先确认目标被接受，再失活 Nav2 并 `SIGSTOP` Gazebo | `55.8 / 300 s` | `nav2_runtime_lost`，`INFRA_UNSTABLE` |

第二条**暂停而非杀死** Gazebo：杀死会触发 campaign 自己的仿真器看门狗，那样这轮
会因为正确的理由但错误的路径结束，什么也证明不了。暂停同时冻结 `/clock`，而中断
的时间戳被拿去和暂停时刻比对——这就把“预算走的是墙钟”从假设变成了断言，也是唯一
单测够不到的性质。首次尝试反而撞上一次 Nav2 bringup 卡死（`change_state` 超时），
探索器正确判为启动超时，但这轮什么也没注入，因此新增 `VOID` 结果与残留进程拒绝。

证据：`docs/results/2026-08-12-nav2-fault-injection-startup.json`、
`docs/results/2026-08-12-nav2-fault-injection-runtime.json`。

**几何**。四处：机器人外接圆从 `0.335` 改为 `0.336`——Nav2 footprint 多边形最远
顶点在 `hypot(0.295, 0.160) = 0.33560 m`，原值比机器人**小** `0.6 mm`，由
`0.15 m` 余量覆盖但方向是错的，现由契约测试锁定（断言不等式而非等于某个手写常量）。
非静态模型不再被静默跳过，改为按 SDF 初始位姿当障碍并加额外余量，另提供
`--reject-non-static`。“什么算地板”从解析器的绝对高度带 `[-0.10, 0.10]` 改为
与参考平面比可通过台阶：原判据只对 z=0 的世界成立，且**失效方向不安全**——一道
`0.08 m` 门槛落在带内，会被当成地面并从障碍列表整个移除。栅格范围从地面平面改为
地面 ∩ 障碍包围盒外扩，并吸附到以世界原点为锚的格网。

三个世界的安全格数在几何整改前后**逐格不变**（`43,396 / 25,030 / 160,567`），
但栅格规模从 `1,400,000 / 4,000,000 / 332,800` 降到
`193,536 / 65,136 / 242,416`——`slam_world` 原本正好压在 4,000,000 上限上，
零余量，现在是 61 倍余量。新位姿另用独立脚本按 SDF 几何复核过，最近障碍分别为
`0.575 / 1.091 / 1.188 m`，要求 `0.486 m`。

### 选择规则的处置与 softmax 的实际上限

据此把 `selection_top_score_band_fraction` 设为 `0.0`，选择即取最佳可达候选。这与
删除机制在行为上完全等价，但保留了旋钮与决策记录；出问题的是宽度不是形状。

softmax 能做到什么，同样按 37 次真实决策回放（`T=2.5`）：

| 决策位置 | 1 | 2 | 3 | 4 | 5 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 触发率 | **0.000** | 0.139 | 0.215 | 0.045 | 0.350 |

**开局它够不到**：p(最佳)≈1，换任何种子都一样。按独立性粗算，到第 3 个目标为止发生
分岔约 `32%`，到第 5 个约 `58%`——即**约四成运行前 5 个目标仍然完全相同**。要让开局
也随机需要 `T≈10–20`，届时全程每次决策多走 `2.9–6.4 m`，而非 `T=2.5` 的 `1.9 m`。

因此结论是：**若目标是每轮路线不同，选择规则不是该动的地方。** 杠杆在上游——改变
出生位姿从第 1 个目标就生效，且不需要机器人主动选一个已知更差的目标；调整评分权重
则改变"什么算好目标"本身。为此出生位姿已成为 launch 参数（`spawn_x/spawn_y/
spawn_yaw`，默认原点，逐级贯通到 `simulation.launch.py`），但**如何选取合法出生点
仍未解决**：随机坐标无法保证落在自由空间内，而从历史目标点取样等于用当前这条固定
路线上的点去检验"能否走出不同路线"，是拿结论当前提。可行的方向是从已建地图的自由
格按余隙筛选采样，尚未实现。

**两批数据的可比性有一处限制**：固定种子那 10 次运行的是跨度式 band（`best−worst`），
新种子这 5 次运行的是 `|best|` 式。同一批 37 次决策上，`f=0.20` 时前者触发 `0.032`、
后者 `0.014`——修正"最差候选决定带宽"那个耦合的同时也改窄了 `0.20` 的实际宽度。
两批的触发率（8.8% 与 4.9%）因此不能直接相减。

逐次决策记录见 `docs/results/2026-08-11-fresh-seed-decisions.log`，两批的目标序列见

## 轮速与 IMU 二维融合对比

自动回归依次静止、直行 6 s，并以 `0.6 rad/s` 原地旋转 4 s。下表记录
旋转段结束时相对 Gazebo 真值的误差；正常和打滑数据来自各自独立运行：

| 条件 | 输出 | 平移误差 | 航向误差 |
| --- | --- | ---: | ---: |
| 正常附着 | 原始轮速 `/wheel/odom` | 0.0008 m | 1.078° |
| 正常附着 | EKF `/odom` | 0.0010 m | 0.009° |
| 正常附着 | 自研 2D SLAM | 0.0062 m | 0.278° |
| 左轮低摩擦 `0.15` | 原始轮速 `/wheel/odom` | 0.0309 m | 13.753° |
| 左轮低摩擦 `0.15` | EKF `/odom` | 0.0309 m | 0.001° |
| 左轮低摩擦 `0.15` | 自研 2D SLAM | 0.0024 m | 0.286° |

Gazebo DiffDrive 与 IMU 消息本身不携带协方差。桥接后先由适配节点按
`config/sensor_covariance.yaml` 写入有限、非零的测量协方差；其中轮速
横向速度方差小于纵向速度方差，以概率形式表达差速底盘非完整约束。
EKF 只采用轮速的平面线速度和 IMU 的偏航角速度；不重复融合轮速偏航，
也不使用 IMU 的绝对姿态或线加速度。它在本次单侧打滑回归中将局部
里程计航向误差从约 `13.75°` 降到 `0.001°`。自研 2D SLAM 已通过激光
匹配把同一打滑测试的最终航向修正到约 `0.29°`，因此短路线的最终
地图/轨迹没有呈现与 EKF 同量级的提升，并会受扫描噪声产生小幅运行间
波动。结论是：IMU 显著增强退化或打滑时的局部运动预测，但不能替代
LiDAR 约束，也不应宣称加入后所有 2D 地图都会更准。面向用户的 2D 启动
入口默认使用 `odometry_mode:=wheel_imu`；冻结的走廊、重复结构和大场景算法
回归显式传入 `odometry_mode:=wheel`，避免历史阈值随上层默认值静默变化。

回归现已具有硬判据而非只打印测量值：两种 profile 都检查适配协方差、
直行平移和旋转航向上限；正常路面要求融合航向相对轮速不劣化超过
`0.5°`，打滑路面要求至少改善 `2°`。

## 旋转与里程计标定

机器人驱动轮几何中心距为 `0.34 m`。考虑 Gazebo ODE 中有限宽圆柱轮的有效接触位置，经过原地旋转标定，差速驱动和里程计使用的有效轮距为 `0.306 m`。该参数不会改变模型几何或 `base_footprint` 的位置。

优化后进行约 127° 原地旋转：

- 轮式里程计相对 Gazebo 真值的航向误差约 `0.31°`。
- SLAM 相对 Gazebo 真值的航向误差约 `0.29°`。
- SLAM 平移偏差约 `1.5 mm`。

SLAM 的旋转关键帧阈值为 `0.05 rad`，用于减小起转和停转时激光相对地图的瞬时偏移。10 Hz LiDAR 与 0.05 m 栅格分辨率下，小角度转弯仍可能出现几厘米的短暂误差，应以停稳后的重新对齐和整张地图是否持续重影作为判断标准。

两点值得单独说。**定位段的精度比建图段更好**（`0.0131` vs `0.0192 m`），这符合预期

论证要防的反面：一个每帧都失配、退回轮速推算的前端在一圈固定数据上也可能看起来够准，
所以接受率必须是独立判据。

证据；`replaceCloud` 会清空关键帧队列，因此 `local_keyframes = 0` 与点数巨大同时
