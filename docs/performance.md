# 性能与旋转标定记录

本文记录 2D/3D SLAM 基线的性能优化和里程计标定结果。数值用于同一测试环境
下的前后对比，不代表所有硬件上的固定性能。

## 性能优化

自研 C++ SLAM 使用 `RelWithDebInfo` 作为默认构建类型，对应 GCC/Clang
常用的 `-O2 -g -DNDEBUG`。复现性能数据前应显式执行：

```bash
colcon build --packages-select slam_robot_slam slam_robot_slam_3d \
  --symlink-install \
  --cmake-args -DCMAKE_BUILD_TYPE=RelWithDebInfo
```

不要使用 `CMAKE_BUILD_TYPE` 为空的构建结果评估扫描匹配性能；这种情况下
GCC 默认等同 `-O0`。

### 自研 3D GICP 前端

2026-08-05 使用同一固定数据集以正式 `1x` 频率运行首版 scan-to-local-map，
收集连续 300 次匹配：

| 指标 | 结果 |
| --- | ---: |
| 真值路线覆盖 | 10.667 m |
| 匹配接受率 | 100.0% |
| 完整回调平均 / P95 | 24.029 / 29.483 ms |
| 末端相对平移误差 | 0.006 m |
| 路段最大平移误差 | 0.007 m |
| 末端相对航向误差 | 0.011° |
| 平移信息特征值比 P05 | 0.1050 |
| 完整信息矩阵最小特征值 | 0.0711 |
| 最小偏航信息量 | 10.6137 |
| 退化误报 | 0 / 300 |

该结果覆盖结构化场景前 10.7 m，不代表闭环 SLAM 精度；当前没有回环或全局
后端。首版曾用 `0.05 s` 最近邻容差直接接受滞后的里程计，因此“没有同步
告警”不能证明同步质量。现在每帧点云必须由前后两条里程计包夹并插值，后
样本尚未到达时进入有界 FIFO；同步异常会落到过期或溢出的可观测告警路径。
合成双平行墙测试的平移信息特征值比低于 `0.01`，而正常路段 P05 为
`0.1050`；默认诊断门限取 `0.05`。该门限用于识别弱方向，并由
`0.01–0.05` 双阈值连续控制该方向的 GICP 修正。

审查探针确认，原实现每帧新建 GICP 对象，使约 2.4 万点目标子图的 20 邻域
协方差每次重算；相同输入的单次 `align` 从冷启动约 `94.8 ms` 降至复用目标
协方差约 `58.4 ms`。正式实现按局部子图版本缓存目标状态，版本改变时才冷
启动。加入缓存、里程计插值和诊断后，同一长走廊两次在线回归 P95 为
`79.187–80.628 ms`，最终复测 951/951 次匹配被接受，未出现同步告警。P95
仍包含关键帧更新导致的冷启动帧，因此长走廊硬门限从 `100 ms` 收紧到
`90 ms`，没有设成不符合实测的 `60 ms`；最大前端间隔门限从 `0.20 s`
收紧到 `0.12 s`。结构化旋转/打滑最终复测 P95 为 `17.460–22.930 ms`，
其门限收紧到 `60 ms / 0.12 s`。

最终方案在信息比不高于 `0.01`（或最小平移信息量不高于 `0.002`）时把弱
方向修正置零，在上限前线性恢复。只用 `ratio/0.05` 的软缩放虽把灾难性
漂移降低很多，但数百帧中残留的小反馈仍会累积，因此没有采用。最终运行的
轮速 + IMU 末端基线误差为 `0.627 m`；前端在出口重新获得端墙约束后修正到
`0.054 m`。严格退化段的处理实际应用率为 `233/233`，入口正常段和明确出口
恢复段均为零误报，最大回调间隔 `0.100 s`。

平行侧墙对横向位移和航向提供强约束，但中段没有可用于估计纵向位移的
几何结构。初版处理对最佳匹配附近的原始相关响应做二维有限差分，以响应
Hessian 的特征值判断平移可观测秩。秩为 1 时移除弱特征向量上的激光
修正，保留该方向的轮式里程计预测；横向和航向匹配不变。输出协方差沿
弱方向从 `0.05 m` 增大到 `0.30 m`。上表记录的是这版实现，其纵向峰值
相对未处理基线下降约 81%。

上表的 392 是激光里程计消息数，不是独立匹配次数：运动不足和拒配路径会
重复发布上一次协方差，因此不能用它推导退化检出率。加入逐次匹配诊断后，
同一默认配置再次执行 25 m 单向回归，共发生 314 次真实匹配，其中 rank 1
为 190 次、rank 2 为 124 次；在这次固定仿真中的检出比例为 60.5%，漏检
比例为 39.5%。ratio 直方图按边界
`[0, .01, .025, .05, .10, .25, .50, 1]` 的计数为
`[91, 29, 70, 94, 30, 0, 0]`。本次纵向峰值 / 最终误差为
`0.130 m / 0.080 m`，横向峰值为 `0.026 m`，无拒配或错误回环。

真实角采样单元测试使用与模型一致的 720 束、stride 2、12 m 量程，覆盖
1/5/20 个关键帧与 `0/0.0025/0.005/0.01 m` 测距噪声。12 种组合中旧版
响应曲面检测器给出 3 次 rank 1、9 次 rank 2；rank 1 时保留了准确的
`0.10 m` 里程计预测，rank 2 时结果被相关匹配拉回 `0.02～0.08 m`。
这说明处理在触发时有效，但响应 Hessian 会把光束端点混叠误当成沿走廊
方向的信息，且结果随子图深度与噪声变化。

当前实现改为在每帧扫描内部保留原始光束索引和量程，只在索引连续且
相邻点距离满足 `0.05 m + 0.05 × range` 的七点窗口中拟合局部直线法向。
归一化矩阵 `Σnᵢnᵢᵀ / N` 的特征值比表示两个平移方向的相对表面支撑，
未归一化特征值则直接表示有效法向数量。弱方向激光修正比例连续取
`min(1, ratio / 0.05)`，避免旧版 rank 硬切换。

上述 12 种组合在新检测器下全部为 rank 1，纵向估计相对准确的
`0.10 m` 预测最大偏差不超过 `0.011 m`，不再随子图深度翻转。最终验收的
25 m Gazebo 回归发生 314 次真实匹配，rank 1 / rank 2 为 `227 / 87`；端墙和
非对称入口/出口锚点可见时存在真实纵向法向，因此 rank 2 是预期结果，
中部长平行墙稳定为 rank 1。物理中段的 188 次真实匹配全部为 rank 1，
检出率 `100%`。本次纵向峰值 / 最终误差为 `0.133 m / 0.123 m`，横向峰值
`0.035 m`，最大前端间隔 `0.100 s`，无拒配或错误回环。正常场景的独立
闸门已加入长闭环和三档快速旋转回归，
两者分别覆盖 209 和 651 次真实匹配，均要求退化误报严格为零。

同一配置随后重复执行单向测试，纵向峰值分别为 `0.210 m` 和 `0.150 m`，
其余横向、航向、前端间隔和无错误回环判据均通过。因此自动回归使用
`0.25 m` 单向连续上限，在保留约 70% 以上基线改善要求的同时覆盖出口
锚点处约一个栅格的运行波动。

### 输入同步率测量

烟雾验收的 1 Hz 无法区分「每帧点云都完成同步」和「多数点云被同步器丢弃」，
因为 `Rtabmap/DetectionRate` 的限速发生在同步回调之后。为把两者分开，把
`Rtabmap/DetectionRate` 临时置 `0`（不限速），此时 `/rtabmap/info` 的发布率
等于同步回调率，可直接与点云率对比。

| 配置 | `/lidar_3d/points` | `/rtabmap/info`（不限速） | `/odom` |
| --- | --- | --- | --- |
| `approx_sync: false`（原配置） | `10.00 Hz` | `10.000 Hz` | `50.0 Hz` |
| `approx_sync: true`（当前配置） | `10.00 Hz` | `10.000 Hz` | `50.0 Hz` |

结论：**精确时间同步在本仿真中并没有丢帧**，回调率等于点云率。原因是
点云时间戳落在整 `100 ms` 栅格上（实测连续戳 `37.300 / 37.400 / 37.500 …`），
而 EKF 以 `50 Hz` 落在 `20 ms` 栅格上，两者恰好成整数倍关系，因此每个点云
时间戳都有一条时间戳完全相同的 `/odom`。

这是巧合而非设计保证：把 `ekf_2d.yaml` 的 `frequency` 改成 `30 Hz` 之类
不整除点云周期的值，或迁移到时间戳不落在公共栅格上的真实硬件，精确同步
会静默失效——表现为输入饥饿而不是报错。因此改用 `approx_sync: true` 并把
`approx_sync_max_interval` 设为 `0.02 s`（`50 Hz` 里程计最坏 `10 ms` 偏差的
两倍，且只有点云周期的 `1/5`，不会跨接到相邻扫描）。改动后回调率不变，
`Did not receive data` 警告为 `0` 次。

### 单圈回环不可靠的归因与 `ProximityPathMaxNeighbors` 反驳

2026-08-05 排查"单圈 proximity 约束时有时无"。原假设是
`RGBD/ProximityPathMaxNeighbors`（配置为 `1`）对稀疏 16 线点云过小。该
假设的两个前提都被推翻。

第一，参数语义理解有误。RTAB-Map 的默认值是 `0`，含义是**禁用** one-to-many
proximity 检测；配置里的 `1` 已经是启用状态，只是每条路径仅合并 1 个邻居
节点，合并后的目标扫描与单帧一样稀疏。

第二，真正的限制是路线几何，与参数无关。用固定包的真值轨迹按
`Rtabmap/DetectionRate=1.0` 与 `RGBD/LinearUpdate=0.10` 复现图节点插入
（模型 `329` 个，实测 `346` 个），再统计"路径距离相差 `20 m` 以上且欧氏
距离在半径内"的历史节点：

| 半径 | 第 1 圈有重访候选的节点 | 第 2 圈 |
| --- | ---: | ---: |
| `10 m`（`RGBD/LocalRadius`） | `18/160`（`11.2%`） | `169/169`（`100%`） |
| `3 m`（与扫描重叠相称） | `3/160`（`1.9%`） | `169/169`（`100%`） |

`72 m` 闭环跑一圈只在最后几秒进入已建图区域，能否命中取决于当时的累计
漂移，因此呈现全有全无的模式，而不是可以调参改善的连续量。

| 栅格 | `28.00 x 16.15 m` | `28.00 x 16.15 m` |
| 自动判据 | 全部通过 | `17/17 PASS` |

`181 -> 185` 是 `2%`，而两次运行的航迹推算漂移本身就差了 `1.328` 对
`0.992 m`，该差异落在运行间噪声内。两圈几何已提供约 `2368` 对候选，瓶颈
不在合并扫描的稠密度，所以参数在这里不起作用。配置保持 `1`，不采用 `10`。

`10` 的代价在 1 Hz 预算内：`361` 帧 RTAB-Map 核心处理均值 `67.6 ms`、
P95 `126.4 ms`、最大 `144.4 ms`，无超过 `200 ms` 的帧。但没有同一套量法的
`1` 对照，因此不宣称 `10` 更快或更慢。

结论：单圈回环不是可以靠调参解决的问题。要做单趟即可验收回环的快速回归，
需要中途折返的路线（8 字形或带返回支路），属于世界设计任务。

### 高度语义 Nav2 自动回归

2026-08-04 在同一 `structured_loop_3d.sdf` 中加入两个互补靶标：

- 高门洞下沿 `0.55 m`，高于 `0.35 m` 机器人和 `0.45 m` 安全扫掠高度；
- 蘑菇柱底座半径 `0.07 m`，但 `z=0.18–0.44 m` 柱帽半径为 `0.40 m`。

`structured_navigation_regression.launch.py` 先执行原有两圈闭环建图，再由
Nav2 完成五个目标。门洞段记录真值穿越截面；柱帽段的直线会穿过粗柱帽，
脚本要求地图环带存在占据单元、机器人与柱心距离至少 `0.55 m`，且向走廊
内侧绕行至少 `0.25 m`。同时要求门洞中心在二维投影中保持自由。

首次完整运行结果：原有建图 `15/15` 判据通过，高度导航 `8/8` 判据通过，
五个 Nav2 目标全部到达。MPPI 在柱帽之后接近最终目标时出现一次
`Failed to make progress`，行为树清图并重新规划后成功完成；Collision
Monitor 没有导致任务失败。回归进程成功退出，结束后未发现残留仿真实例。

```bash
ros2 launch slam_robot_slam_3d structured_navigation_regression.launch.py
```

手动在线导航复测发现一条此前回归未覆盖的失效路径：RTAB-Map 默认允许六自由度
ICP，运行一段时间后实测 `map -> odom` 达到 `z=0.167 m`、横滚
`-0.71°`，而 `odom -> base_footprint` 仍严格为二维。这个小倾角足以让远处
地面返回越过 `0.05 m` 地面阈值；全局 PointCloud2 障碍层出现围绕机器人的
同心弧线，并把可通行走廊连成 `NO_VALID_PATH (208)`。

临时把地面阈值提高到 `0.10 m` 仍无法消除远距离倾斜误差，因此没有采用
“继续抬高过滤阈值”的掩盖方案。正式修复是启用 `Reg/Force3DoF=true` 与
`RGBD/ForceOdom3DoF=true`，保持三维点云地图但约束平面机器人轨迹；结构化
回归同时新增 `map -> odom` 高度峰值不超过 `0.02 m`、横滚/俯仰峰值不超过
`0.5°` 的硬判据。清空旧数据库后再次手动建图和导航，原先的地面同心弧假
障碍消失，蘑菇柱附近可正常规划和通行；完整自动长回归仍由上述新增判据持续
覆盖。

纯 LiDAR RTAB-Map 不依赖相机才能建图，但没有图像时视觉词袋回环与视觉重定位
被禁用，回环范围收窄为空间 proximity 预测加 3D ICP 验证。运行中的
`Missing visual features` 提示对应这一能力边界，不表示当前 LiDAR ICP 回环
失败；后续相机用于增强全局地点识别。

### EKF 周期裕度与一次测量方法教训

首次在导航链路上观察到 `7` 次 `Failed to meet update rate`（最长
`0.224 s`）并一度记为「叠加 Nav2 后的已知资源竞争」。复查后确认**这个
结论是错的，起因是测量环境本身被污染**：用于收尾的
`kill -INT <ros2 launch pid>` 并不会回收该 launch 的子进程树，于是先前
几次运行遗留的 Gazebo、RTAB-Map、EKF 和桥接进程一直在后台运行。故障
被发现时机器上同时存在 `5` 个 `gz sim` 实例和多个 `ekf_filter_node`，
系统负载 `55`。多个 EKF 同时向 `/odom` 和 `/tf` 发布，测到的超时是这些
互相竞争的实例造成的，与本项目的配置无关。

改用 `setsid` 让每次运行独占一个进程组、结束时按进程组整体回收，并在
每次运行后校验无残留进程，重新测量：

| 运行环境 | 时长 | EKF 周期超时 |
| --- | --- | --- |
| 污染环境（多实例并行） | — | `7` 次，最长 `224 ms` |
| 隔离运行，静态 DDS 图 | `90 s` | `0` 次 |
| 隔离运行，反复起停 `ros2` CLI 进程 | `44 s` | `0` 次 |
| 隔离运行，全程 | `137 s` | `1` 次，`24 ms` |

隔离后唯一一次超时是 `24 ms`（目标周期 `20 ms`，超出 `4 ms`），发生在
驱动进程加入 DDS 图的瞬间。**完整 Nav2 + RTAB-Map + Gazebo 链路在本机
留有充足的 EKF 周期裕度**，不存在需要整改的资源竞争。

留下的教训与 SLAM 本身无关但会反复出现：`ros2 launch` 在非交互 shell
中被后台执行时，向其 PID 发 `SIGINT` 不足以终止整棵进程树；一个泄漏的
仿真实例足以在不报任何错的情况下让后续所有时序测量失真。现有回归脚本
（如 `corridor_regression`）是由 launch 文件拉起的 ROS 节点，由 launch
系统负责回收，不受此影响；受影响的只是手工用 shell 拉起仿真的临时测量。

## 轮速与 IMU 二维融合对比

自动回归依次静止、直行 6 s，并以 `0.6 rad/s` 原地旋转 4 s。下表记录
旋转段结束时相对 Gazebo 真值的误差；正常和打滑数据来自各自独立运行：

| 条件 | 输出 | 平移误差 | 航向误差 |
| --- | --- | ---: | ---: |
| 正常附着 | 原始轮速 `/wheel/odom` | 0.0008 m | 1.078° |
| 正常附着 | EKF `/odom` | 0.0010 m | 0.009° |
| 正常附着 | 自研 2D SLAM | 0.0062 m | 0.278° |
| 左轮低摩擦 `0.15` | 原始轮速 `/wheel/odom` | 0.0309 m | 13.753° |
| 左轮低摩擦 `0.15` | EKF `/odom` | 0.0309 m | 0.001° |
| 左轮低摩擦 `0.15` | 自研 2D SLAM | 0.0024 m | 0.286° |

Gazebo DiffDrive 与 IMU 消息本身不携带协方差。桥接后先由适配节点按
`config/sensor_covariance.yaml` 写入有限、非零的测量协方差；其中轮速
横向速度方差小于纵向速度方差，以概率形式表达差速底盘非完整约束。
EKF 只采用轮速的平面线速度和 IMU 的偏航角速度；不重复融合轮速偏航，
也不使用 IMU 的绝对姿态或线加速度。它在本次单侧打滑回归中将局部
里程计航向误差从约 `13.75°` 降到 `0.001°`。自研 2D SLAM 已通过激光
匹配把同一打滑测试的最终航向修正到约 `0.29°`，因此短路线的最终
地图/轨迹没有呈现与 EKF 同量级的提升，并会受扫描噪声产生小幅运行间
波动。结论是：IMU 显著增强退化或打滑时的局部运动预测，但不能替代
LiDAR 约束，也不应宣称加入后所有 2D 地图都会更准。面向用户的 2D 启动
入口默认使用 `odometry_mode:=wheel_imu`；冻结的走廊、重复结构和大场景算法
回归显式传入 `odometry_mode:=wheel`，避免历史阈值随上层默认值静默变化。

回归现已具有硬判据而非只打印测量值：两种 profile 都检查适配协方差、
直行平移和旋转航向上限；正常路面要求融合航向相对轮速不劣化超过
`0.5°`，打滑路面要求至少改善 `2°`。

## 旋转与里程计标定

机器人驱动轮几何中心距为 `0.34 m`。考虑 Gazebo ODE 中有限宽圆柱轮的有效接触位置，经过原地旋转标定，差速驱动和里程计使用的有效轮距为 `0.306 m`。该参数不会改变模型几何或 `base_footprint` 的位置。

优化后进行约 127° 原地旋转：

- 轮式里程计相对 Gazebo 真值的航向误差约 `0.31°`。
- SLAM 相对 Gazebo 真值的航向误差约 `0.29°`。
- SLAM 平移偏差约 `1.5 mm`。

SLAM 的旋转关键帧阈值为 `0.05 rad`，用于减小起转和停转时激光相对地图的瞬时偏移。10 Hz LiDAR 与 0.05 m 栅格分辨率下，小角度转弯仍可能出现几厘米的短暂误差，应以停稳后的重新对齐和整张地图是否持续重影作为判断标准。

## 复现基础运动测试

短时发送直行指令：

```bash
ros2 topic pub /cmd_vel geometry_msgs/msg/Twist \
  "{linear: {x: 0.20}, angular: {z: 0.0}}" -r 10
```

结束速度发布后发送一次零速度：

```bash
ros2 topic pub /cmd_vel geometry_msgs/msg/Twist \
  "{linear: {x: 0.0}, angular: {z: 0.0}}" --once
```

测试时应同时记录 Gazebo 真值、`/odom`、SLAM 位姿、实时率以及相关进程 CPU，占用变化需要在相同场景和显示配置下比较。
